# Обновления Textora через GitHub Releases

## Что внедрено

Sparkle 2.10.0, **Check for Updates…** в меню и Settings → System,
настройка автоматической проверки. Sparkle спрашивает разрешение на фоновые
проверки; стандартный интервал — 5 часов. Установка требует действия пользователя.
Настройку проверок хранит сам Sparkle.

Постоянный адрес ленты:
`https://github.com/MasterHrust/Textora/releases/latest/download/appcast.xml`.
Каждый стабильный Latest-релиз должен содержать **Textora.dmg и appcast.xml**.
Список изменений берётся из Markdown-описания GitHub Release и встраивается в
appcast. Sparkle показывает его прямо в окне обновления перед установкой.
Изменять Swift-код или пересобирать уже установленное приложение для этого не нужно.
Ссылки на DMG внутри ленты привязаны к конкретному тегу. Сервер и Pages не нужны.

## Один раз перед первой публикацией

Команды выполняются из каталога macOS-приложения.

1. Загрузить зависимость и инструменты:

   ```bash
   xcodebuild -resolvePackageDependencies -project Textora.xcodeproj -scheme Textora -clonedSourcePackagesDirPath .deriveddata-updates/SourcePackages
   ```

2. Создать ключ в macOS Keychain:

   ```bash
   .deriveddata-updates/SourcePackages/artifacts/sparkle/Sparkle/bin/generate_keys --account Textora
   ```

   Вставить напечатанный **публичный** ключ в `SUPublicEDKey` файла
   `Sources/Info.plist`. Публичный ключ Textora уже настроен для версии 1.1;
   на текущем Mac закрытый ключ находится в Keychain под аккаунтом `Textora`.
   Эти шаги нужны только при первоначальной настройке; на другом Mac следует
   импортировать сохранённый ключ, а не создавать замену.
   Закрытый ключ остаётся в Keychain. Сохранить резервную копию в защищённом
   хранилище вне репозитория; экспорт поддерживается через `generate_keys -x`.
   Не генерировать новый ключ для каждого релиза.

3. Проверить Developer ID signing и нотариализацию приложения вместе со
   встроенным Sparkle. Подпись обновления не заменяет подпись Apple и
   нотариализацию. Сохранять bundle ID `com.textora.app` и команду Apple Developer.
4. Проверить доступность релизов без входа в GitHub. Для приватного репозитория
   нужны публичные файлы обновлений и соответствующие URL.

## Каждый следующий релиз

1. В `Sources/Info.plist` увеличить `CFBundleVersion` (1 → 2 → 3…), а
   `CFBundleShortVersionString` выставить в пользовательскую версию (например 1.1).
   Номер сборки должен превышать все ранее опубликованные номера.
2. Собрать Release, подписать Developer ID, нотариализовать и подготовить DMG.
   Образ должен содержать новую `Textora.app` со встроенным Sparkle.framework.
   При упаковке сохранять symlinks и executable permissions.
3. Создать **draft** GitHub Release с нужным тегом и заполнить описание
   пользовательских изменений. Это источник текста и для страницы GitHub, и для
   окна обновления. Использовать заголовки и списки Markdown, например:

   ```markdown
   ## New
   - My Style: profiles for all apps or individual applications.
   - Message: turn spoken thoughts into a draft before inserting.

   ## Improved
   - More reliable text insertion.

   ## Fixed
   - Reduced interference with typing.
   ```

   Коммиты сами по себе не становятся release notes. Описание можно заполнить
   через GitHub или создать draft из отредактированного Markdown-файла:

   ```bash
   gh release create v1.4.0 --repo MasterHrust/Textora --draft --title 'Textora 1.4.0' --notes-file RELEASE_NOTES_1.4.0.md
   ```

   Перед использованием локального файла убрать технические сведения о
   кандидатах и тестировании, которые не предназначены пользователям.

4. Подготовить файлы в **новом** каталоге:

   ```bash
   bash Scripts/prepare-update.sh v1.4.0 Textora.dmg /tmp/textora-v1.4.0
   ```

   По умолчанию скрипт читает описание указанного GitHub Release через
   `gh release view`. Нужны установленный и авторизованный GitHub CLI, Python 3
   и инструменты Sparkle. GitHub Release при этом не изменяется.

   Для локальной подготовки без GitHub можно передать Markdown четвёртым
   аргументом; при публикации использовать тот же текст в описании релиза:

   ```bash
   bash Scripts/prepare-update.sh v1.4.0 Textora.dmg /tmp/textora-v1.4.0-preview RELEASE_NOTES_1.4.0.md
   ```

   Скрипт сначала сохраняет описание рядом с образом как `Textora.md`, затем
   запускает `generate_appcast --embed-release-notes`. Ключ `Textora` остаётся в
   Keychain. Если инструменты расположены иначе, задать `SPARKLE_BIN`.

   Полученная лента содержит `<description sparkle:format="markdown">` со
   списком изменений, а также ссылку на всю историю релизов. XML после подписи
   **не переписывается**. Проверяются версия, размер DMG, наличие EdDSA-подписи
   и точное содержимое встроенного списка. Без непустого описания подготовка
   останавливается до подписи. Скрипт не собирает, не нотариализует и не
   публикует приложение.

5. Загрузить **Textora.dmg и appcast.xml из выходного каталога** в draft Release.
   `Textora.md` - необязательная копия для проверки; отдельная загрузка для
   отображения изменений не требуется. Проверить версию, номер сборки,
   минимальную macOS, подпись, ссылку на DMG и список изменений. Опубликовать
   стабильный релиз с отметкой **Latest**.
6. Проверить постоянный URL ленты, скачивание DMG и отображение списка в окне
   обновления на предыдущей версии. Опубликованный DMG не заменять: подпись
   соответствует точным байтам файла. Для изменения приложения выпустить
   следующую сборку.

Если описание GitHub Release изменилось после генерации, автоматически изменить
уже подписанный `appcast.xml` оно не может. Повторить подготовку в новом каталоге
с **тем же неизменённым DMG** и загрузить обновлённый `appcast.xml`. Сам DMG
пересобирать и заменять ради изменения текста не нужно.

## Обзор после установки обновления

Обзор открывается один раз для новой `CFBundleShortVersionString`, после
завершения первого обучения и настройки нужных разрешений. Номер сборки
`CFBundleVersion` отображается в About, но его изменение само по себе не
повторяет обзор. Отдельного пункта в меню нет; повторное открытие доступно в
Settings → About & Updates → What’s New.

Содержимое берётся локально из **Resources/ReleaseNotes.md**, без запроса к
GitHub при запуске. Первая строка должна совпадать с версией приложения:

```markdown
# Textora 1.4.1

A maintenance update.

## Fixed
- Describe the user-visible fix here.
```

Для выпуска только с исправлениями достаточно раздела Fixed: окно покажет
список без предложений настраивать старые функции. Разделы My Style, Message
и Recent Results получают ссылки на соответствующие настройки. Если файл
отсутствует или версия не совпала, старый обзор автоматически не показывается;
в About остаётся ссылка на историю GitHub. Тест проверяет соответствие
встроенного файла версии приложения.

Для следующего выпуска обновить Version/Build и Resources/ReleaseNotes.md.
Затем использовать этот же Markdown как описание GitHub Release
(`--notes-file Resources/ReleaseNotes.md`) и при локальной подготовке
`prepare-update.sh` четвёртым аргументом. Так текст до и после установки
остаётся одинаковым. Только изменение номера версии не создаёт список
изменений: его содержание нужно написать перед сборкой.

## Локальные проверки релизных скриптов

```bash
python3 -m unittest discover -s Scripts -p 'test_release_notes.py' -v
bash -n Scripts/prepare-update.sh
```

Тесты не обращаются к GitHub, Keychain или реальным DMG: подставные инструменты
проверяют передачу Markdown, обязательность списка, экранирование, соответствие
версии и отсутствие изменений XML после генерации. Реальная проверка подписания
и окна обновления выполняется отдельно на подготовленных сборках.

## Проверка перед первым публичным выпуском

Использовать две подписанные и нотариализованные сборки с одинаковым bundle ID,
публичным ключом и возрастающими номерами. Для репетиции задать отдельную
HTTPS-ленту через `SUFeedURL` в тестовых сборках.

- Установить старую сборку в Applications и вызвать Check for Updates.
- Проверить заголовки и список изменений прямо в окне обновления.
- Проверить ссылку на всю историю релизов.
- Проверить скачивание, установку, перезапуск и номер новой версии.
- Проверить настройки, доступ к API-ключам, Accessibility и запуск при входе.
- Проверить отсутствие обновлений на новой версии и ошибку при недоступной сети.
- Проверить сохранение выбора автоматических проверок после перезапуска.
- Проверить отказ от пакета, изменённого после подписи.

Полную установку нельзя проверить одной неподписанной локальной сборкой.
Первую версию со Sparkle существующие пользователи устанавливают вручную.
